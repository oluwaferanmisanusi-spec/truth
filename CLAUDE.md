# Truth — barbershop booking website

Single responsive Next.js website with four areas: customer booking flow, customer accounts, barber schedule, owner admin. Customer and barber screens are designed at phone width, owner screens at desktop width (the owner dashboard stays computer-only; on a phone it isn't usable, decided 2026-10-27). Nothing is a native mobile app.

## Stack (decided 2026-10-19/20; backend moved to NestJS 2026-10-24)
- **Website** (repo root): Next.js 16 App Router, TypeScript, Tailwind 4. A pure frontend: pages and server actions call the API through `lib/api/client.ts` (forwards the visitor's Supabase access token). Tokens live in `app/globals.css` (`@theme`), fonts Fraunces (display) + Inter in `app/layout.tsx`. Port 3100: `npm run dev`.
- **API** (`server/`; renamed from `api/` on 2026-10-29 because Vercel turns a top-level `api/` folder into website functions): NestJS 12 (ESM, `.js` import endings, Vitest, oxlint). Port 3200: `npm run dev:api`. All database writes, Paystack, Resend and one-time links happen here. Global `AuthGuard` locks every route unless `@Public()`; `@Roles('owner', 'manager')` for owner-dashboard routes (`@Roles('owner')` for owner-only ones), `@Roles('barber')` for barber routes; Zod schemas via `@Body/@Query/@Param({ schema })`. Reply shapes in `server/src/contracts/` are imported by the website as types (`@api/*`).
- **Supabase** for Postgres + auth. Log in / log out stay website → Supabase directly (sets the session cookie); the API verifies the token with `getClaims`. Browser/website use the public anon key only (`lib/supabase/client.ts`, `server.ts`).
- **Secrets**: only `server/.env` (template `server/.env.example`) — service-role key, DB URL, owner login, Paystack secret, Resend key. The website's `.env.local` (template `.env.local.example`) holds no secrets. Never print either file.
- Vercel for hosting (free Hobby plan, 4 projects: `truth-web-staging` and `truth-api-staging` deploy the `staging` branch, `truth-web` and `truth-api` deploy `main`; the API projects use Root Directory `server`; on Vercel `server/src/main.ts` exports the app instead of listening, see its comment), Resend for email, Paystack **test mode** for payments (naira, "Secure payment by Paystack" copy in the design). Paystack webhook goes to the API: `POST /webhooks/paystack`.
- Scripts (read `server/.env`): `npm run create-owner`, `npm run sample-bookings` (adds paid guest bookings ~3 weeks ahead; safe to rerun), `npm run db:types` (writes the types for both API and website).
- Seed data = the design's dummy data (shop at 14 Example Street, Lekki; barbers Tunde Adeyemi, Kemi Bello, Femi Okafor, Sola Ade; services Haircut ₦6,000/30 min, Skin fade ₦8,000/45 min, Beard trim and shape ₦4,000/20 min, Haircut and beard ₦10,000/60 min, Kids' cut ₦5,000/30 min). Time zone: Africa/Lagos (WAT). Sola has no bookings, as in the design.

## Business rules from the design
Rule numbers live in `shop_settings` and on-screen/email wording reads them (website: `lib/rules.ts`; API: `ShopInfoService`); don't hard-code them. 10-minute slot hold before payment. Pay in full at booking. Cancel or reschedule ≥24 h before for full refund, otherwise no refund, unless the shop used "Ask to reschedule" (owner Bookings → Cancel, 2026-10-26: reasons dialog, email with a link; until the appointment the customer may move for free or cancel for a full refund; the booking shows "Reschedule asked" until moved; `bookings.reschedule_*`, `request_token_hash`; the emailed link stops working once the booking is moved or cancelled, 2026-10-27). 15-minute no-show grace period; barber can mark completed/no-show only after the appointment start. Guest bookings get an emailed link; signing up with the same email merges them. Barber invites expire in 7 days, password reset links in 1 hour, email verification links in 24 hours. Owner sets opening hours per weekday, holidays, and time zone. Changing hours or adding a holiday never moves existing bookings; Shop settings keeps showing the upcoming ones that now fall on a holiday or outside opening hours, with links to them in Bookings, until they're cancelled or moved (2026-10-26). Shop closed on Sundays in seed data.

Screens (2026-11-01): each booking shows one status (`displayStatus` in `components/status-badge.tsx`): Booked (stored as `confirmed`), Needs outcome (booked and started; owner and barber screens only), Reschedule asked (on every screen, customer and barber included, until it's moved, cancelled or started), Refund failed, Pending payment, Completed, No-show, Cancelled; the owner's status filter lists exactly the bookings showing that status, plus "Upcoming" (everything not started yet), which the barber page and Shop settings link to. Barbers are linked to a service from either the service form or the barber page. Notices about something that just happened use `<Toast>` (slides down from the top, closes on the next click); `<Alert>` is for notices that describe the page.

Barber decisions (2026-10-24): barber logins are barber-only (`profiles.role = 'barber'`); we assume a barber is never also a customer. Barber access needs that role plus an active `barbers` row linked by `profile_id` (`Me.barberId`); a deactivated barber can't use the schedule or log in. The owner can't invite an email that already has a customer account. Barbers land on `/barber`, can't open My bookings, and book as a guest if they ever use the booking flow. The owner and managers are treated the same way on the shop pages (2026-10-26): My bookings and Log in take them to `/owner/bookings`, and they book as a guest. Whole-day blocks must start at least `shop_settings.leave_notice_days` (3) days ahead; part-of-day blocks have no notice rule. Invites are emailed via Resend and the owner still gets a copy link. Blocks can't overlap live bookings (checked in the database, with a trigger so a booking can't land in a block either); whole-day blocks skip closed days. Outcomes are final. Unrecorded outcomes show as reminders on the barber's schedule and the owner's Bookings page ("Needs outcome" filter); an end-of-day reminder email comes with the Phase 6 cron jobs.

Managers (2026-10-24, not in Figma; built from owner components): `profiles.role = 'manager'` uses the owner dashboard with the owner's powers (bookings, stats, services, barbers, settings) except managing managers. Only the owner invites (`manager_invites`, hashed token, 7 days, emailed + copy link, `/owner/invite/[token]`), resends, cancels and removes managers (2026-10-26: managers can no longer remove each other). Removing deletes the login, so their session stops at once. A manager's email must not already have an account. Managers log in and reset passwords on the owner screens.

Suggestion for later (not built): one login per person, so a barber who is also a customer keeps one account. Barber access would come only from the active `barbers` row; after login, people who are both would get a "My schedule / My bookings" switch, and deactivating a barber would remove the schedule but leave them a customer. An invite to an email with an account would be accepted by logging in. (Built briefly on 2026-10-24 and removed, see git history of commit 6bdcd99.)

## Security and jobs (Phase 6, 2026-10-25)
- Scheduled jobs (free plans, 2026-10-28): Vercel Hobby only allows daily crons, so a GitHub Actions workflow (`.github/workflows/scheduled-jobs.yml`, added during deployment setup) calls `/jobs/tidy` (hourly: expire holds, check payments Paystack never reported, retry refunds that failed to send, clear old tokens and counts) and `/jobs/outcome-reminders` (18:00 UTC = 19:00 WAT, barbers only). They need `CRON_SECRET`.
- Attempt limits: `@RateLimit(...)` on a route, counted in the database (`rate_limits`), per visitor IP (IPv6 by /64), email or user. The website forwards the visitor IP with `INTERNAL_API_KEY`; both keys are required when `NODE_ENV=production`. The website asks `POST /login-attempts` before each log in. Holds (2026-10-27): a visitor can make 10 holds in 15 minutes, counting only ones still unpaid (`bookings.held_by`, a hash of their network, cleared by `/jobs/tidy` once the hold ends), plus 40 per hour; going back or paying frees one straight away, so customers comparing times and phones sharing a mobile network's address aren't blocked.
- Sessions: the API refuses a token whose Supabase session is gone (log out, password reset, removed manager); a password reset logs the account out everywhere. Log out ends only that device's session (`signOut({ scope: "local" })`, 2026-10-27).
- One login per browser, shared by all tabs (2026-10-26). `SessionGuard` (root layout) checks the login when a tab comes back into view and, if another tab switched or logged out, covers the page with a "Reload page" dialog. To review two roles at once, use a private window or another browser.
- No two-step login (2026-10-26): built for the owner and managers (authenticator app, remembered devices) and removed at the user's request; the owner and managers log in with email and password. See git history of commit e15ffb0 if it's wanted again.
- Payments and refunds (2026-10-27): a payment arriving after its hold ran out is confirmed only if that time could still be booked now (`record_payment` re-checks with `available_slots`), otherwise refunded in full. The payment row is saved before Paystack is asked for a checkout, so every payment can be matched. A refund that doesn't go through is retried by `/jobs/tidy` (`REFUND_TRIES` = 4, at least 6 h apart), then `gave_up_at` is set and the owner is emailed; owner Bookings shows a "didn't go through" reminder, a "Refund failed" label and filter, and "Mark as refunded" (`settled_by_hand_at`) after the owner refunds in Paystack. `CRON_SECRET` isn't set locally, so the jobs only run on the live site.
- The public booking page (`GET /holds/:id`) shows the customer's email only while it's a hold; after that it's masked.
- Website security headers are in `next.config.ts`. Supabase public sign-up must stay off (dashboard: Authentication → Sign In / Providers); all accounts are made by the API.

## Keeping this repo safe
This file, `AGENTS.md` and everything else in git are readable by anyone with repo access. Never put secrets (keys, passwords, database URLs), real customer or barber data, or the owner's real login in them; use the dummy data above. Real values live only in `server/.env` (and `server/.env.production` for the live database) and `.env.local`, which git ignores; share them with a developer through a password manager, never chat, email or an issue.
